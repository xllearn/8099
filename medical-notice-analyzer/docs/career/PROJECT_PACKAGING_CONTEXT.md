## 2. 已确认的业务数据

- 数据覆盖约 32 个省级单位、333 个市级单位、2800 个县级单位，以及国家医疗保障局、卫生健康相关单位和大型医疗机构。
- 日采集公告约 9000～10000 条。
- 正式进入 AI 分析链路的任务通常每天 10 份以内。
- 单个公告通常包含 0～10 个附件，多数为 0～4 个附件。
- 主要公告类型为带量采购、集中采购及接续采购。
- 单份正式报告通常为 2000～5000 字，至少 4～5 个章节；表格数量取决于公告是否含适合结构化展示的数据。
- 原人工流程通常需要 2～3 人协作约 2 小时；系统目标是缩短至分钟级生成和人工复核。
- 当前内部使用人员约为测试人员 2～3 人、业务人员 3～5 人。

### 2.1 已确认模型口径

- 报告生成：官方 API `model` 字段为 `deepseek-v4-pro`。
- 质检与修订：官方 API `model` 字段为 `deepseek-v4-flash`。
- DeepEval Judge：公司部署的 GLM-5 与 DeepSeek V4 Flash。

`model` 字段表示调用模型 API 时指定的模型标识，而不是简历中的营销名称。

## 3. 当前仓库可验证实现

当前项目本质是医疗公告证据约束分析和报告生成系统，主要链路为：

```text
数据库选择公告
  -> 读取公告正文和附件元数据
  -> 下载并按格式解析附件
  -> 构建完整 Evidence Pack
  -> 根据输入限制生成紧凑证据视图
  -> 后端代理 Dify Workflow 生成报告
  -> 输出 Markdown 与 ReportIR
  -> 执行本地质量门和结构修复
  -> 必要时进行受控修复
  -> 保存运行状态、检查点和历史版本
  -> 用户反馈后生成修订版本
  -> 受控导出 Word
  -> DeepEval 非阻塞旁路评测
```

### 3.1 当前技术特征

- FastAPI 作为服务端 API 和编排入口。
- MySQL 读取公告正文和附件元数据。
- 针对 PDF、Word、Excel、CSV、HTML、ZIP 等格式使用专用解析逻辑。
- Evidence Pack 采用 A/B/C 证据分层：
  - A：原文、表格单元格等直接证据；
  - B：基于 A 的结构化事实；
  - C：摘要、指导、诊断等辅助内容。
- 完整证据包与发送给模型的紧凑输入分离。
- 生成结果包含 Markdown 和结构化 ReportIR。
- 当前已经存在质量门、Claim-Evidence Index、修复、运行状态、检查点、历史对比、报告记忆和用户反馈修订能力。
- 当前 DeepEval 为独立、非阻塞的 advisory sidecar，不影响正式报告交付。
- 当前前端为原生 HTML/CSS/JavaScript 管理页面，不是求职包装重点。

## 4. 简历假设完成的目标架构

为了面向 Agent、AI 应用和 AI 后端岗位，项目按以下方向包装为已完成状态：

### 4.1 DeepEval 质量评测体系

- 引入 DeepEval 离线回归和线上异步评测。
- 建立 Faithfulness、Critical Fact Coverage、Attachment State Consistency、Answer Relevancy 等指标。
- 进一步扩展 Contextual Precision、Contextual Recall、结构完整性、数值准确性和用户修订成功率。
- 评测结果不阻塞主流程，但可以触发告警、回归分析和版本对比。

### 4.2 事实与分析分层

- 事实层只能输出有 A/B 级证据支持的内容。
- 分析层允许基于事实进行推理，但必须引用结构化事实。
- 使用置信度、风险等级、未知条件和人工复核门禁控制可靠性。
- 高风险字段包括价格、数量、时间、企业、产品、资质和中选条件。

### 4.3 LangGraph Agent Orchestration

采用固定工作流型 Agent 为主，而不是完全自由规划 Agent：

```text
load_materials
  -> parse_attachments
  -> build_evidence
  -> compress_evidence
  -> extract_facts
  -> generate_report
  -> quality_review
  -> repair / human_review / persist_result
```

LangGraph 中：

- State：当前任务共享数据快照；
- Node：执行具体步骤的函数；
- Edge：决定下一步走向的规则；
- Checkpoint：可恢复的 State 历史快照。

### 4.4 模型抽象调用层

统一封装模型调用，支持：

- DeepSeek V4 Pro、DeepSeek V4 Flash、GLM-5；
- 结构化输出；
- 超时和重试；
- 并发限制；
- Token 统计；
- Prompt、模型和工作流版本记录；
- 模型降级和异常分类。

### 4.5 Celery + Redis 异步任务体系

- FastAPI 只负责创建任务和返回 `run_id`。
- Celery Worker 后台执行 LangGraph。
- Redis 作为 Broker、短期缓存和分布式锁。
- DeepEval 放入低优先级评测队列。
- 附件较多时可以并行解析。
- MySQL 保存最终业务状态，不能只依赖 Celery Result Backend。

### 4.6 MySQL + MinIO + Redis 多级存储

- MySQL：任务元数据、状态、版本、索引、评测汇总和关系数据。
- MinIO：原始附件、解析产物、完整 Evidence Pack、Compact Payload、ReportIR、Markdown、Word/PDF。
- Redis：消息队列、短期缓存、进度、锁和热点结果。
- 使用 Transactional Outbox、内容哈希、幂等键和补偿任务处理跨存储一致性。

### 4.7 OpenTelemetry 全链路可观测性

贯通：

- FastAPI 请求；
- Celery 任务；
- LangGraph 节点；
- 模型调用；
- MySQL、Redis 和 MinIO；
- DeepEval 评测。

记录 Trace、Metric 和结构化日志。前端 Trace 页面不是简历重点，重点描述后端 Trace 数据采集和查询能力。

## 5. RAG 与辅助材料自动选择方案

### 5.1 最新产品边界

所有外部用户使用**同一份共享资料体系**：

1. 公开项目公告资料库；
2. 公司审核并指定的行业知识库。

明确不支持：

- 用户个人上传 PDF、Word、Excel 等文件；
- 用户建立个人或企业私有知识库；
- 不同客户之间维护独立知识空间。

可以支持：

- 用户选择系统已有公告；
- 用户手动输入分析目标、问题或修订意见；
- 用户手动选择系统已有辅助材料；
- 系统自动推荐辅助材料；
- 用户对系统推荐结果进行增删确认。

用户输入的文字属于当前任务指令或反馈，不自动沉淀为共享知识库事实。

### 5.2 RAG 在项目中的作用

RAG 不是简单地给模型增加历史文本，而是负责：

- 发现当前公告的补充、更正、结果和执行公告；
- 召回上一轮或同类集采项目；
- 召回相关政策、地区规则和业务解释；
- 召回公司审核过的历史分析和知识条目；
- 为用户的反馈修订补充新的证据；
- 将召回资料重新构建为可追溯 Evidence。

推荐流程：

```text
主公告 + 用户分析目标
  -> 查询理解和检索条件生成
  -> 混合检索（关键词 + 向量 + 结构化过滤）
  -> 重排
  -> 展示候选材料及召回原因
  -> 用户确认或系统自动选材
  -> 构建任务级 Evidence Pack
  -> 生成、质检和评测
```

### 5.3 自动召回材料字段

| 字段 | 含义 |
|---|---|
| `document_id` | 系统资料唯一标识 |
| `document_title` | 资料标题 |
| `document_type` | 公告、政策、历史分析、规则卡片等资料类型 |
| `retrieval_reason` | 为什么召回该资料 |
| `retrieval_score` | 综合相关性评分 |
| `relation_type` | 补充公告、历史轮次、同地区、同品类等关系 |
| `source_scope` | `public_notice` 或 `company_curated` |
| `effective_date` | 资料生效日期，用于防止引用过期规则 |
| `selected` | 是否进入最终 Evidence Pack |

## 6. 公司指定的付费知识库设计

公司知识库必须是经过审核、可追溯、可版本化的内容，而不能只是把所有历史报告直接放进向量库。

### 6.1 推荐的核心知识库类型

#### A. 集采项目关系与时间线知识库

包含：

- 同一项目的征求意见、正式公告、补充、更正、中选、执行和接续文件关系；
- 上一轮与下一轮项目关系；
- 项目阶段、关键节点和截止日期；
- 地区、品类和项目轮次关联。

用户价值：快速回答“当前公告和上一轮有什么变化”“后续还会有哪些节点”。

#### B. 政策规则标准化知识库

将长政策转换为标准规则卡片：

- 申报主体要求；
- 产品和注册证要求；
- 报价和最高有效申报价；
- 中选规则；
- 采购量和协议量规则；
- 配送、执行和价格联动；
- 信用评价、失信约束和取消资格；
- 新获批产品、非中选产品和补充申报规则。

用户价值：不只搜索原文，而是直接得到结构化规则和原文出处。

#### C. 地区准入与挂网规则知识库

包含各省市：

- 挂网和申报流程；
- 价格治理要求；
- 配送和采购规则；
- 医保编码和注册证要求；
- 规则变化历史；
- 地区之间的差异对比。

用户价值：帮助企业判断不同地区的准入要求和差异。

#### D. 历史中选、价格与采购量知识库

包含公开资料中可合法使用的：

- 历史中选企业和产品；
- 中选价格、报价区间和价格变化；
- 采购量、约定采购量和执行周期；
- 品类、地区、项目轮次和时间维度的统计。

用户价值：为报价、市场判断和历史对比提供数据依据。

#### E. 企业、产品与编码主数据知识库

包含：

- 企业标准名称及别名；
- 产品标准名称、规格型号和品类；
- 注册证、备案号和医保编码；
- 企业、产品、注册证、编码之间的映射；
- 数据变更和有效状态。

用户价值：解决不同公告命名不一致、同一产品难以关联的问题。

#### F. 公司审核历史分析知识库

只纳入经过业务专家审核的高质量内容：

- 历史项目分析结论；
- 项目变化总结；
- 企业注意事项；
- 规则之间的关联解释；
- 可复用的分析框架。

每条内容必须保留：来源公告、分析人员、审核状态、适用时间和版本。

用户价值：让系统输出具有行业经验，而不只是复述公告。

#### G. 风险规则与案例知识库

包含：

- 常见申报遗漏；
- 报价风险；
- 资质不匹配；
- 价格联动风险；
- 配送和执行风险；
- 公开的失信、取消资格和处罚案例；
- 风险触发条件和建议动作。

用户价值：将报告升级为可操作的风险提示。

#### H. 业务术语与规则本体知识库

包含：

- 带量采购、联盟采购、接续采购等概念；
- 字段同义词和公告表达差异；
- 企业、产品、价格、数量、时间等统一 Schema；
- 公告类型和项目阶段分类；
- 关系类型和风险标签。

用户价值：提高检索、结构化抽取和跨项目关联准确率。

#### I. 专家问答和标准处置知识库

来源于经过审核的高频业务问题：

- 某类企业是否可以申报；
- 注册证变更如何处理；
- 报价与历史低价冲突如何判断；
- 补充公告发布后应重新关注什么；
- 某项目和上一轮如何串联分析。

用户价值：支持直接问答和报告中的建议章节。

#### J. 数据质量与异常修复知识库

包含：

- 常见乱码、字段缺失和附件异常；
- 企业/产品别名映射；
- OCR纠错词典；
- 公告重复和版本识别规则；
- 已确认的数据修复记录。

用户价值：提高上游 Evidence Pack 的完整性和准确率。

### 6.2 推荐的首期付费知识库组合

首期不建议同时建设全部十类。最有商业价值、也最容易和现有公告数据结合的是：

1. **集采项目关系与时间线库**；
2. **政策规则标准化库**；
3. **历史中选、价格与采购量库**；
4. **公司审核历史分析库**；
5. **风险规则与案例库**。

这五类可以形成核心付费能力：

```text
项目全生命周期追踪
+ 规则快速解读
+ 历史数据对比
+ 专家分析复用
+ 风险提示
```

### 6.3 付费产品形态建议

虽然所有用户使用同一份资料库，仍可以按功能和使用额度收费：

- 基础版：公告检索、单公告摘要、有限次数报告生成；
- 专业版：自动辅助材料召回、历史项目对比、政策规则库和完整报告；
- 高级版：价格/采购量分析、风险知识库、多项目关联分析、批量任务和数据导出；
- API版：为企业系统提供检索、项目关系、规则卡片和报告生成接口。

不通过“每个客户独占资料”收费，而通过：

- 知识深度；
- 分析能力；
- 任务额度；
- 批处理能力；
- 导出和 API 能力；
- 项目跟踪和提醒能力；
- 响应速度与服务保障。

## 7. 用户反馈修订链路

当前仓库已经支持用户文字反馈后修订报告。目标架构中，应将反馈分为两类：

### 7.1 不需要新增检索

例如：

- 内容更简洁；
- 增加表格；
- 调整章节；
- 修改表达；
- 突出企业注意事项。

输入为：

```text
当前报告 + 用户反馈 + 原 Evidence Pack
```

### 7.2 需要新增检索

例如：

- 增加与上一轮集采的串联分析；
- 对比其他地区规则；
- 补充历史中选和价格情况；
- 结合公司知识库增加风险提示。

流程为：

```text
用户反馈
  -> 意图分类
  -> RAG 召回公司统一资料库
  -> 生成新增 Evidence
  -> 合并 Evidence Pack
  -> 只重写相关章节或生成新版本
  -> 重新质检和 DeepEval
```

每次修订必须保存：反馈文本、召回材料、前后版本差异、修订模型、质检结果和最终是否采纳。

## 8. 指标口径

### 8.1 报告质量指标

- Claim Support Rate：报告断言中有 A/B 证据支持的比例。
- Critical Fact Coverage：应覆盖关键事实中实际被覆盖的比例。
- Unsupported Claim Rate：无证据断言比例。
- Numeric/Date Exact Match：价格、数量、日期等关键字段准确率。
- Section/Topic Completeness：必需章节和主题完整率。
- First-pass Quality Gate Pass Rate：首轮质检通过率。
- Revision Acceptance Rate：用户反馈后一次修订通过率。

### 8.2 检索和 Evidence 指标

- Contextual Precision：召回内容中真正相关内容的比例和排序质量。
- Contextual Recall：应召回的关键信息是否被召回。
- Source-to-Evidence Precision：证据包提取事实的准确率。
- Source-to-Evidence Recall：原始资料中的关键事实有多少进入证据包。
- Mandatory Evidence Retention：压缩后强制证据保留率。
- Attachment Parse Success Rate：附件解析成功率。

### 8.3 系统工程指标

- API 提交 P95；
- 队列等待 P95；
- 端到端任务 P50/P95/P99；
- 任务最终成功率；

## 9. 推荐简历项目定位

### 项目名称

**基于 LangGraph 与 Evidence Grounding 的医疗采购公告分析 Agent 平台**

### 一句话定位

面向医疗器械带量采购和集中采购场景，独立设计并实现基于证据约束、自动资料召回、Agent编排和大模型质量评测的公告分析平台，将公告正文、附件、历史项目和公司行业知识转化为可追溯的结构化报告，并通过异步任务、分层存储和全链路可观测性保障生产运行。

### 商业化升级叙事

> 将原本仅供内部业务人员使用的公告报告生成工具，升级为面向企业客户的共享行业知识分析平台；基于公开公告库和公司审核知识库，通过 RAG 自动召回历史项目、政策规则、价格采购量数据和风险案例，为报告生成、跨项目对比和用户反馈修订提供证据支持。
