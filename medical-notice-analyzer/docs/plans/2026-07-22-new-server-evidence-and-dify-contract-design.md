# 新服务器证据包、自包含报告与 Dify 输出契约设计

日期：2026-07-22
状态：方案 B 已获用户口头批准，等待书面设计复核
目标分支：`codex/new-server-87-medical-notice-analyzer-20260722`

## 1. 背景与目标

新环境 `192.168.34.87:8099` 使用新 Dify，字符档位为 160000、220000、240000，UTF-8 硬上限为 870400 字节。当前代码仍会把新环境的证据包上限与旧的 80000 字符 VBP 常量取最小值，导致新环境最终输入包仍只有约 7.8–7.9 万字符。

浙江样本还暴露了两个独立问题：

1. 附件解析主要保留表头、统计值和少量样例，没有稳定保留“企业—产品—需求量”的完整行级关系，后续模型只能基于残缺摘要写作。
2. 新 Dify 虽然开启 structured output，后续 Code 节点仍从 LLM 的 `.text` 中截取第一个闭合 JSON；极短修订只要非空，就可能覆盖完整初稿。

本设计同时解决以下目标：

- 新环境仅在证据包超过 240000 字符时执行字符二次压缩，并尽可能压到接近 240000 字符。
- 旧环境 `192.168.34.88:8099` 的 65000、75000、80000 档位和行为保持不变。
- 报告正文自包含，不设置附录，不展示页码、表格编号、单元格位置或其他溯源信息。
- 明细过多时允许正文只列示部分企业、产品和需求量，但所有行必须在系统内部参与计算和分析。
- 禁止用“详见附件”“请查阅原附件”“以正式文件为准”等措辞替代核心事实。
- 降低 Dify QA 截断、JSON 契约错配和极短修订覆盖完整初稿的发生率，并在仍发生时阻断错误结果。

## 2. 范围与非目标

### 2.1 本次范围

- 新环境证据包的字符/字节预算和二次压缩策略。
- 规则解析、内部规范表、语义列映射、聚合与正文明细选择。
- 报告生成、QA、修订提示词的自包含契约。
- Dify structured output 读取、QA 路由、修订验收和后端二次校验。
- 对应的本地自动化验证和文档更新。

### 2.2 非目标

- 不修改旧环境容量策略或旧 Dify 工作流。
- 不把完整逐行明细放入附录；本设计明确不生成附录。
- 不在正式报告中输出页码、附件名、表格 ID、行列号或来源哈希。
- 不让大模型负责抄写或计算完整企业/产品/需求量表。
- 设计和实施阶段不自动部署服务器，不自动导入或发布线上 Dify。

## 3. 总体方案

采用“规则保真 + LLM 语义映射与写作 + 确定性质量门”的组合架构：

1. 规则解析器读取并保留全部可解析行、原始单元格值、规范数值和单位。
2. 当规则无法可靠识别含混表头时，调用公司内部 DeepSeek 模型，只返回列语义映射和表格角色，不返回或改写事实值。
3. 后端根据规范表计算总量、数量、占比、集中度和分类分布，并确定正文需要展示的代表性行。
4. Dify 只接收汇总事实、确定性选出的正文明细和必要政策证据，负责分析与行文。
5. Dify 与后端分别执行输出契约校验；无效修订不能覆盖已验收初稿。

## 4. 新环境二次压缩设计

### 4.1 环境隔离

- 不全局把 `compact_pack.py` 的旧默认硬上限改成 240000。
- `main.py::_compact_evidence_pack_for_dify_uncached` 使用本次请求已计算的 `target_max_chars` 作为 VBP 执行上限；`target_max_chars = min(平台字符上限, DIFY_EVIDENCE_PACK_HARD_MAX_CHARS, 显式 max_chars)`，未提供显式 `max_chars` 时忽略该项。
- 新环境默认得到 240000；旧环境通过配置显式得到 80000。
- mandatory evidence 上限明确为 `target_max_chars - 1000`：旧环境保持 79000，新环境默认使用 239000。最小可行 mandatory 包超过本次字符硬限或 UTF-8 字节硬限时立即失败。
- 提升 `COMPACT_RULE_VERSION`，避免新环境复用旧规则生成的约 8 万字符缓存。

### 4.2 触发与目标

- 默认新环境中，`first_stage_chars <= 240000`：不触发字符二次压缩；显式传入更低 `max_chars` 时以该请求的 `target_max_chars` 为触发线。
- 默认新环境中，`first_stage_chars > 240000`：触发字符二次压缩。
- 仅当 `target_max_chars=240000` 时，字符软目标区间为 238000–239000，硬上限为 240000。旧环境和显式较低 `max_chars` 继续使用其既有分级窗口，不套用 24 万软目标。
- UTF-8 字节数大于 866304 时启动 byte-overflow 收缩，目标为不超过 866304 字节，最终硬上限为 870400 字节。
- 字符未超限、仅字节超过 866304 时，执行 byte-overflow 收缩，但不标记为字符二次压缩。如果完整 mandatory 包无法降至字节软目标、但仍不超过 870400 字节且 retention 为 1.0，可以接受并记录内部软目标警告；超过 870400 字节必须失败。

`first_stage_chars` 和 `first_stage_bytes` 均由同一个 `canonical_compact_json()` 结果计算。该函数固定为 `json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(", ", ": "))`；字符数取该字符串的 Python `len()`，字节数取同一字符串的 UTF-8 编码长度。字符判断、字节判断、缓存键和测试必须调用同一函数。对象中的尺寸字段应迭代回写直至数值稳定，再执行 240000/240001 等边界判断，避免元数据回写改变判定结果。

### 4.3 压缩算法

1. 先保留 mandatory evidence：公告核心事实、关键规则、企业/产品/需求量聚合、必要字段语义和完整证据依赖闭包；mandatory retention 必须严格等于 `1.0`，不能沿用“达到 90% 即通过”的宽松语义。
2. 对 optional evidence 按确定性优先级排序：高价值事实、分类汇总、代表性明细、解释性段落、重复或低价值材料。
3. 使用预算驱动的迭代/二分收敛选择 optional evidence，避免一次性过度压缩。
4. 若压缩结果明显低于软目标且仍有可加入的完整证据块，则按优先级回填，直至再加入下一块会超过 ceiling。238000–239000 是尽力目标；当完整证据块粒度导致无法填满时，选择不超过 ceiling 的最大完整块集合，不为追求字符数破坏事实边界。
5. 不对 JSON 或正文做裸字符串截断，不拆断字段、表格行或 UTF-8 字符。
6. mandatory evidence 自身超过硬限制时返回受控错误，不生成表面成功但事实残缺的输入包。

压缩元数据记录原始字符数、最终字符数、字节数、触发原因和规则版本，仅用于内部诊断，不进入正式报告。

## 5. 行级事实与公司 DeepSeek 模型

### 5.1 内部规范表

附件解析结果增加内部 `canonical_tables`：

- 保存每张核心表的列、全部已解析行、规范化数值、单位和内部来源定位。
- 记录源行数、成功解析行数、重复/空行处理结果和规范化行哈希。
- 机器验收不变量为：`eligible_rows == aggregated_rows`、`selected_rows + excluded_rows == eligible_rows`，且 `selected_rows` 必须是 `eligible_rows` 的子集。空行、重复行和不完整行分别计数；核心表存在无法确定处置的不完整行时阻断交付。
- 内部来源定位只用于诊断与校验，不进入 compact Dify 输入中的报告正文材料，也不渲染到最终报告。
- 只有完整行关系参与后续聚合，不能用字段样例值拼接企业、产品和需求量关系。

### 5.2 模型职责

公司模型配置：

- Base URL：`http://192.168.34.97`
- Model ID：`elian-deepseek-v4-flash`
- API Key：仅通过运行时秘密环境变量 `EVIDENCE_SEMANTIC_LLM_API_KEY` 注入，仓库和文档不保存真实值。

模型只在规则映射不确定时执行以下任务：

- 识别多行或含混表头的语义角色，例如企业、产品、规格、需求量、单位、价格、状态。
- 判断一张表是否属于本公告的核心企业/产品/需求量表。
- 返回严格结构化的候选列映射和简短理由。

模型不得：

- 生成、补齐或修改企业名称、产品名称、数量、价格或单位。
- 计算合计、占比或排序。
- 把缺失值推断为已披露事实。

后端只接受能通过确定性检查的映射：必需语义列唯一、目标列确实存在、数值解析率和单位一致性达标。无法通过时转人工复核，不让模型自由补全。

模型接口是否兼容 OpenAI API 路径和响应格式，需要在实施阶段以无业务数据的最小请求只读确认；确认前不写死 `/v1/chat/completions` 等路径。

### 5.3 凭据与传输安全

- API Key 不写入 Git、`.env.example` 的真实值、Dify DSL、诊断 JSON 或应用日志。
- 日志必须屏蔽 `Authorization`、API Key 和原始鉴权错误正文。
- Key 只注入 analyzer 后端服务，不注入 Dify、前端或其他容器。
- 客户端只允许精确 origin `http://192.168.34.97`（默认 80 端口）和确认后的 API 路径，禁止跨主机或跨 scheme 重定向，并关闭自动重定向。
- 客户端使用 `trust_env=false` 或等价的固定 no-proxy 策略，避免 `Authorization` 被系统代理转发。
- API 路径确认前不得携带 Key 逐路径探测；应先由接口文档、服务管理员或不带鉴权的元数据确认准确路径。
- 当前地址使用 HTTP，凭据在传输层不加密。正式启用前必须验证网络 ACL，并由用户明确接受受信内网中的明文传输风险；优先由网关提供 HTTPS。

## 6. 无附录的自包含报告设计

### 6.1 正文必须完整表达的内容

- 公告主体、时间、适用范围、执行条件、责任主体、关键程序、例外和后果。
- 企业数量、产品数量、需求总量及单位。
- 主要分类分布、需求集中度、最高/最低或异常情况，以及对相关主体的影响。
- 能支持报告结论的企业—产品—需求量代表性明细。

### 6.2 明细选择

当全部明细可在正文预算内清晰呈现时，尽量全部列示。超过正文明细预算时，由后端确定性选择：

1. 所有异常状态、缺失状态、特殊资格或政策例外行。
2. 需求量最高的行和形成高集中度的主要行。
3. 每个主要产品类别至少一条代表行。
4. 数值为零、明显极端或会改变结论的行。
5. 在剩余正文预算内按需求量和分析价值继续加入。

正文可以说明：“本次共涉及 N 家企业、M 个产品、T 条有效明细，正文列示 K 条关键明细，其余 T-K 条已纳入汇总统计与分析。”N、M、T、K 和 T-K 均由后端确定性计算并校验，不得由模型自行生成。不得要求用户另行查看公告或附件。

### 6.3 禁止措辞与质量门

正式正文阻断以下外部依赖措辞及语义等价变体：

- “详见附件”“详见附件清单”
- “请查阅/参阅原始附件”
- “具体企业/产品/需求量需查看附件”
- “相关信息以附件为准”
- “以正式文件/官方文件为准”

解析/OCR/模型置信度等技术限制只进入内部 diagnostics，不进入正式报告。由于“不支持事实自动修复/删除”开关已关闭，质量门发现违规措辞或核心事实缺失时必须阻断交付，不能通过删句伪装为合格报告。

## 7. Dify structured output 与修订契约

### 7.1 Contract V2

Generate、QA、Revise 后续节点优先直接读取 LLM 的 `structured_output` 对象，不再把 `.text` 作为主路径。最终输出增加：

- `contract_version`
- `body_source`
- `report_complete`
- `report_chars`
- `report_sha256`
- `initial_report_chars`
- `initial_report_sha256`
- `parent_version`
- `parent_report_chars`
- `parent_report_sha256`
- `pack_id`
- `run_id`
- `validation_errors`

模型只负责生成 `report_markdown` 等内容候选；上列合同字段全部由确定性验收 Code 节点生成，模型自报值一律不采信。`body_source` 只能是 `generation_validated`、`revision_validated`、`validated_generation_retained` 或 `fallback_unvalidated`；`validation_errors` 只保存脱敏错误码，不保存原始模型输出或鉴权信息。

报告生成/修订正文末尾必须包含内部完整性标记 `<!-- REPORT_COMPLETE_V2 -->`。统一规范化与验收顺序如下：

1. 检查该标记是最后一个非空白内容，随后只移除这一个标记。
2. 将 CRLF 和 CR 统一为 LF，再对整个正文执行一次首尾空白清理；不做 Unicode 归一化或其他内容改写。
3. 规范化后的正文定义为 `canonical_report_body`；`report_chars` 使用 Python `len(canonical_report_body)` 的 Unicode code point 口径。
4. `report_sha256 = SHA256(canonical_report_body.encode("utf-8"))`，不包含完整性标记。
5. 后端在 `_clean_model_output` 或任何其他内容变换之前执行同一规范化并复核字符数和哈希。V2 已验收正文不得再被静默清洗；确需清洗时必须形成新候选并重新通过全部合同和质量门。

### 7.2 兼容路径

如果实际新 Dify 版本无法让 V2 Code 节点直接选择 `structured_output`：

- 兼容解析必须要求整个非空文本恰好是一个 JSON 对象。
- 禁止继续使用“找到第一个左花括号并截取首个闭合对象”的逻辑。
- 兼容结果仍必须通过与 V2 相同的字段、完整性和长度检查。

### 7.3 修订验收

修订稿只有同时满足以下条件才能覆盖初稿：

- schema、必填字段和类型正确。
- 完整性标记存在。
- 必需章节和关键事实仍被覆盖。
- 修订稿字符数不少于已验收初稿的 65%。
- Code 节点计算的字符数和哈希与最终传输结果一致。
- `pack_id`、`run_id` 必须与当前请求严格相等；`parent_version`、`parent_report_chars` 和 `parent_report_sha256` 必须与当前最后一个已验收版本严格相等，再以该直接父版本计算 65% 保留率。

3 字、304 字、跨 pack/run、基于过期父版本或其他异常结果即使 JSON 合法也不能覆盖初稿。修订无效时保留最后一个已验收版本，`body_source=validated_generation_retained`，状态改为 `needs_manual_review`；该版本不能冒充已经通过最终质量门的完成报告。只有不存在任何已验收正文时才进入受控 fallback，`body_source=fallback_unvalidated`，状态为失败或人工复核且不可作为最终报告下载；fallback 也不得把证据包字典直接作为正式正文。

### 7.4 QA 降低截断概率

- 将事实/证据检查与结构/风格检查拆分或分别约束输出。
- QA issue schema 明确字段、严重等级、必填项和 `additionalProperties: false`。
- 限制 issue 数量及单项文本长度，避免 4096 token 被大量重复问题耗尽。
- 每个 QA 节点使用独立的 QA Contract V2：`qa_contract_version`、`qa_complete_marker`、`qa_rule_manifest_sha256`、`rule_results` 和受限的 `issues`。`rule_results` 必须对该节点负责的每个 `rule_id` 恰好返回一项，不得缺失、重复或包含未知规则；`qa_complete_marker` 必须等于固定值 `QA_COMPLETE_V2`。
- QA 规则全集和 `qa_rule_manifest_sha256` 由上游 Code 节点确定性生成；下游验收节点重新计算 manifest 哈希、核对规则 ID 集合并产生 `qa_contract_ok`，不采信模型自报的完成状态。拆分 QA 时，合并节点必须确认每个子 QA 的合同均完整且规则全集并集与本轮要求严格相等。
- QA `finish_reason=length`、schema 错误或解析失败时，只允许重试 QA 一次；仍失败则转人工复核。
- QA 传输/解析失败不能伪装成报告内容问题并路由到 Revise。
- 无论是否保留了已验收正文，当前轮任一 QA 在重试后仍发生传输、截断或解析失败，都必须 `needs_manual_review`，不能视为本轮 QA 通过或自动交付。
- 只有实际 Dify 版本能够将节点内部 `finish_reason` 暴露给验收节点时才使用它；不可见时，以 structured output 缺失、schema 不完整、QA marker/manifest 不匹配或规则结果集合不完整作为硬失败信号，不能依赖无法取得的字段。

### 7.5 后端独立防线

- V2 输出由后端重新计算字符数和哈希，并核对完整性状态。
- V2 的 `.text` 兼容路径执行严格整对象解析。未发布 V2 前，legacy 最终输出已经丢失内部原始 `.text` 和准确父版本信息，后端只能执行 pack-aware 动态最短长度、报告结构、异常碎片和状态兜底，不能声称已证明“整对象解析”或准确的 65% 修订保留率。
- 首对象截取问题、父版本绑定和准确修订比例只有在 Dify V2 发布后才能完全关闭；后端 legacy 防线只能降低错误结果被交付的概率。
- Dify 输出不满足契约时映射为 schema/truncation 错误，不能返回 `finished`。

`status=finished` 的充分必要条件为：存在 V2 已验收正文，当前轮所需 QA 全部合同有效且质量门通过；无需修订时使用 `body_source=generation_validated`，完成修订并通过二次 QA 时使用 `body_source=revision_validated`。QA 失败、无效修订后保留旧正文、fallback 或任一合同错误都不能返回 `finished`。

## 8. 错误处理

必须阻断自动交付的情况包括：

- 核心附件下载、解析或表格识别失败。
- 企业、产品、需求量等必需列不能唯一映射。
- 全部行未参与聚合，或数量/单位无法闭合校验。
- 证据压缩移除了 mandatory evidence 或超过字符/字节硬限制。
- 报告正文含外部依赖措辞。
- QA 输出截断或合同无效（即使仍保留一个已验收旧正文，也必须转人工复核，不能自动交付）。
- 修订契约无效且不存在可保留的已验收版本。

非核心背景材料缺失可以记录内部警告，但不得在正式报告中暴露技术诊断。

## 9. 验证策略

实施阶段先编写会失败的本地自动化检查，再修改实现。最低覆盖：

- 新环境 240000 字符不触发字符二压，240001 字符触发；完整证据块粒度允许时收敛到软目标区间，否则得到不超过 239000 的最大完整块集合。
- 新环境 80001–240000 字符不再被旧 VBP 上限压到约 8 万。
- 旧环境 80000 字符合同保持不变。
- mandatory evidence 超过 8 万但低于新环境上限时能够完整保留。
- 字符与 UTF-8 字节限制同时满足，仅字节超限时使用正确的触发原因。
- 多行表头、重复企业、多 sheet、单位列和异常行能够形成完整内部规范表。
- 正文明细过多时只展示确定性选中部分，但汇总计算使用全部行。
- 正文不包含附录、页码、表格溯源和外部依赖措辞。
- `.text` 含多个 JSON 时只使用有效 structured output；极短修订不能覆盖初稿。
- QA 截断只触发 QA 重试/人工复核，不触发内容修订。
- QA `finish_reason` 不可见且 JSON/schema 表面合法、但 marker、manifest 或任一必查 `rule_id` 缺失时，仍必须判定 QA 合同失败。

上述验证仅针对本地代码和 DSL 合同；线上新 Dify 单节点确认、浙江样本重跑和服务器部署需另行明确授权。

## 10. 变更边界与建议顺序

1. 在新服务器代码分支实现证据包阈值隔离和后端 fail-closed 防线。
2. 实现内部规范表、规则聚合、DeepSeek 语义映射适配器和正文明细选择。
3. 修改生成/QA/修订提示词及正式正文安全门。
4. 修改 Dify DSL 为 Contract V2，并保留后端 V1/V2 双读。
5. 完成本地自动化验证和安全扫描，确认 Git 中不存在真实 API Key。
6. 经用户明确授权后，先部署兼容后端，再在新 Dify 草稿验证 structured output 选择器，最后发布工作流并执行受控样本验证。

## 11. 验收标准

- 新环境不会再因旧 80000 字符常量生成约 7.9 万字符输入包。
- 超过 240000 字符的输入在 mandatory evidence 可容纳、完整证据块粒度允许时收敛至约 238000–239000 字符；无法精确填满时取不超过 239000 的最大完整块集合，且任何情况都不得超过 UTF-8 硬上限。
- 旧环境的 80000 字符行为没有变化。
- 报告不含附录、页码、表格编号、来源定位或引导用户查看原公告/附件的措辞。
- 全部可解析企业/产品/需求量行参与内部聚合；正文只在明细过多时选择性展示。
- 纯 LLM 不承担行级事实提取或数值计算；模型语义映射不能改变原始事实值。
- QA 截断或修订解析异常不会再生成或接受 3 字、304 字等极短完成报告。
- 无效修订不能覆盖最后一个已验收正文。
- 仓库、提交历史、日志和 DSL 中均不存在真实 API Key。
- 未经另行授权，不修改线上 Dify、服务器部署或旧环境。
