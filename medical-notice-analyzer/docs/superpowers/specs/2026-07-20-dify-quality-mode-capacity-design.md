# Dify 新版质量模式扩容设计

## 1. 目标

将 `medical-notice-analyzer` 从旧版 Dify 的约 8 万字符输入策略切换到新版 Dify 1.14.2 的质量优先策略，在不改变前端交互、不增加“速度/质量”选择按钮的前提下：

- 后端继续完整保存原始 `evidence_pack`。
- 发送给 Dify 的紧凑证据包正常目标提升到 16 万字符。
- 复杂材料允许安全压缩到 22 万字符，单次调用硬上限为 24 万字符。
- 除字符数外，同时限制 UTF-8 字节数，避免中文和 JSON 开销突破 Dify HTTP 节点约 1 MiB 的文本限制。
- 保留现有“生成、质检、必要时修订、复检”的质量链路。
- 修订任务复用同一份受控紧凑证据包，禁止绕过限制发送完整证据包。
- 新 Dify API 密钥只保存在后端运行环境，不进入源码、测试、文档或日志。

## 2. 非目标

本次不包含：

- 前端质量/速度模式按钮。
- 快速模式、跳过质检或切换低成本模型的工作流分支。
- 将所有文件解析、OCR、ZIP、Excel 行数限制统一放大。
- 扩大最终报告目标长度、用户反馈长度、报告记忆或模型输出上限。
- 删除旧的 URL 分析流程。
- 在源码或 Dify DSL 中写入任何真实 API 密钥。

## 3. 输入容量与配置

新增或调整以下运行配置：

| 配置 | 默认值 | 含义 |
|---|---:|---|
| `DIFY_PLATFORM_STRING_MAX_CHARS` | `400000` | 新版 Dify 平台字符串上限，仅用于诊断和容量说明 |
| `DIFY_FULL_INPUT_MAX_CHARS` | `160000` | 低于该值时尽量完整保留高价值证据 |
| `DIFY_SAFE_COMPACT_MAX_CHARS` | `220000` | 中大型材料的安全压缩目标 |
| `DIFY_EVIDENCE_PACK_HARD_MAX_CHARS` | `240000` | 应用单次 Dify 输入字符硬上限 |
| `DIFY_EVIDENCE_PACK_HARD_MAX_BYTES` | `870400` | 850 KiB UTF-8 字节硬上限 |
| `DIFY_TIMEOUT_SECONDS` | `600` | 常规质量任务请求超时 |
| `DIFY_LARGE_INPUT_TIMEOUT_SECONDS` | `900` | 超过 22 万字符或进入真实分阶段处理的任务请求超时 |
| `DIFY_WATCHDOG_GRACE_SECONDS` | `30` | 看门狗相对实际请求超时的额外等待 |

兼容规则：

- 旧配置 `DIFY_VARIABLE_HARD_MAX_CHARS` 作为 `DIFY_EVIDENCE_PACK_HARD_MAX_CHARS` 的兼容别名；新配置存在时优先使用新配置。
- 配置值必须满足 `完整输入阈值 <= 安全压缩阈值 <= 应用硬上限 <= 平台上限`。
- 字符硬上限与字节硬上限同时生效，任意一个超限都不能发送。
- `870400` 字节为应用保护值；Dify HTTP 节点仍可保留约 1 MiB 平台限制，为 JSON 包装和协议开销预留空间。

## 4. 证据包构建

### 4.1 完整包与紧凑包分离

后端持久化的完整 `evidence_pack` 不做总字符截断。`GET /analysis/packs/{pack_id}` 只返回为 Dify 构建的紧凑包。

紧凑包必须记录：

- `compact_pack_chars`
- `final_dify_input_chars`
- `compact_pack_bytes`
- `final_dify_input_bytes`
- 字符与字节使用率
- 输入策略
- 压缩原因
- 被省略内容和影响范围

字符数按最终 JSON 字符串计算，字节数按同一 JSON 字符串的 UTF-8 编码计算，两个值必须基于完全相同的序列化方式。

### 4.2 动态预算

不再依赖旧版 8 万字符档的固定正文和附件上限。以当前允许的总字符预算为基础，按证据价值进行初始分配：

- 主材料正文与规则：35%
- 主材料核心附件：45%
- 辅助材料：8%
- 指引、警告、元数据和 JSON 结构预留：12%

预算允许回流：某一类证据未用完的预算优先转给主材料核心附件，其次转给主材料正文；辅助材料不得挤占主材料预算。

核心附件的初始内容规则：

- 核心附件摘要：2400～3000 字符。
- 关键事实：最多 20 条。
- 重要章节：最多 16 段，每段 600～800 字符。
- 单个核心附件正常预算 24000 字符，必要时可提升至 36000 字符，但始终服从全局字符和字节硬限制。
- 普通主材料附件正常预算 12000 字符，最多 18000 字符。
- 辅助附件正常预算 6000 字符，最多 8000 字符。
- 表格证据保留字段结构、统计、关键列和代表值，不发送完整行级数据。

### 4.3 收缩顺序

当最终 JSON 超过字符或字节目标时，按以下顺序收缩：

1. 去除重复模板、免责声明和重复段落。
2. 缩短辅助材料正文，保留相关片段和摘要。
3. 缩短普通附件摘要。
4. 缩短非核心表格描述，但保留字段结构和统计。
5. 收缩核心附件的低相关章节。
6. 最后才收缩主材料正文尾部，并记录需要人工复核的风险。

收缩循环结束后如果仍超过任一硬限制，必须返回受控错误或进入真实分阶段处理；不得像当前逻辑一样记录残余超限后继续发送。

## 5. 大材料质量处理

两个主材料不再仅因为数量为二就自动标记为 `staged_generation`。输入策略首先依据最终证据价值、字符数、字节数和附件结构决定。

当材料无法在 24 万字符或 850 KiB 内安全表达时，质量模式需要真正的两阶段处理：

1. 按主材料和核心附件分别生成带证据引用的结构化摘要。
2. 使用结构化摘要综合生成最终报告，再执行质量检查。

如果新版 Dify 工作流暂未增加真实分阶段节点，后端必须明确返回“材料超过单次质量输入上限”的可诊断错误，不能把“提示模型分阶段思考”描述为已完成真实分阶段生成。

## 6. 修订链路

当前用户反馈修订会把完整 `evidence_pack` 作为 Dify 输入变量发送，可能产生多 MB 请求并绕过紧凑包限制。修改后：

- 修订请求仅发送 `pack_id`、`run_id`、反馈、当前报告和必要的记忆字段。
- Dify 通过既有 HTTP 节点按 `pack_id` 获取同一质量策略的紧凑证据包。
- 如果工作流契约暂时必须接收 `evidence_pack`，后端只能传入按同一配置重新构建并通过字符/字节校验的紧凑包。
- 修订反馈继续限制为 4000 字符。

## 7. 超时与重试

- 最终紧凑包不超过 22 万字符时，使用 600 秒请求超时。
- 超过 22 万字符、接近字节硬上限或进入真实分阶段处理时，使用 900 秒请求超时。
- 看门狗时间始终等于实际请求超时加 30 秒，不得再用 300 秒上限提前终止 600～900 秒的请求。
- 大输入质量任务最大自动尝试一次，避免官方模型调用在不确定状态下重复计费。
- 常规任务保留现有重试策略。

## 8. 诊断与运行记录

诊断输出增加：

- 最终字符数和 UTF-8 字节数。
- 字符/字节上限及使用率。
- 主正文、核心附件、普通附件、辅助材料的预算和实际占用。
- 省略内容类型、原因和风险。
- 是否需要人工复核。
- 是否因为超限拒绝发送。

告警以字符或字节使用率任一超过 90% 为触发条件。运行记录保留质量模式配置快照，保证首次生成、重试、恢复、诊断和修订使用一致的容量规则。

## 9. Dify 接入

- 后端 `DIFY_BASE_URL` 指向新版 Dify API。
- `DIFY_WORKFLOW_API_KEY` 使用用户提供的新应用 API 密钥，只写入 `.env` 或服务器环境变量。
- 前端继续只调用后端，不接触 Dify 密钥。
- Dify HTTP 节点继续请求 `GET http://192.168.34.88:8099/analysis/packs/{pack_id}`。
- 本地 DSL 变更必须导入并发布到新版 Dify 后才算生效。
- 切换前验证新 API Key 对应已发布的目标应用，避免密钥属于错误应用。

## 10. 测试与验收

### 10.1 自动测试

至少覆盖：

- 159999、160001、219999、220001、239999、240001 字符边界。
- 全中文、emoji、引号、反斜杠和换行导致的 UTF-8/JSON 大小差异。
- 850 KiB 字节边界，即使字符数未超限也必须拦截。
- 单主材料、双主材料、附件主导、表格主导和十个辅助材料。
- 未使用预算向主材料和核心附件回流。
- 收缩后仍超限时禁止调用 Dify。
- 修订链路不再发送完整证据包。
- 600/900 秒请求策略与 630/930 秒看门狗策略。
- 诊断阈值使用新配置，不再硬编码 75000/80000。

### 10.2 真实联调

使用三个脱敏或内部允许的真实样本验证约 16 万、22 万和 24 万字符输入：

- Dify 成功获取紧凑包。
- 紧凑包末尾哨兵证据仍能在模型输出或质量检查中被引用。
- 报告不是片段，不从中间章节开始。
- 正式报告正文不出现技术实现说明。
- 记录取包、首次生成、质检、修订和总耗时。
- 验证失败时保留旧应用回退配置。

## 11. 完成标准

只有同时满足以下条件才视为完成：

- 所有新增和受影响测试通过。
- 全量测试通过。
- `.env.example`、Docker 配置、README 和代理规范中的容量说明一致。
- 源码、测试、文档和 Git diff 中不存在真实 API 密钥。
- 新 Dify 应用 API 调用成功。
- 16 万和 22 万真实样本完成质量流程；24 万样本至少完成容量与超时验证。
- 生产切换后 `/health`、证据包接口和报告生成链路均通过 GET/真实业务请求验证。
