# Dify 生成加只读质检精简设计

## 1. 目标

在新服务器 `.87` 的 `medical-notice-analyzer` 中，将首次报告工作流从：

`生成 -> 首轮质检 -> 必要时自动修订 -> 二次质检 -> 输出`

精简为：

`生成 -> 首轮只读质检 -> 输出`

首轮质检只识别问题、决定状态和记录诊断，不得修改、删除或覆盖首次生成正文。旧服务器 `.88`、旧 Dify、容量策略、证据包构建和 DeepSeek 摘要开关均不改变。

## 2. 背景与已确认根因

同一份浙江材料的两次新环境运行使用了相同证据内容，但最终报告分别约为 1800 字和 4300 字。

- 第一次采用 Dify 正常输出。
- 第二次的修订节点返回了语法可解析、但语义上只是提示词或 JSON 契约片段的 `report_markdown`。
- `Parse Revision JSON` 只在 JSON 解析抛出异常时保留旧正文；对“合法 JSON 中的非空碎片正文”不会回退。
- `Final Revised Result` 优先采用任何非空修订正文，因此碎片覆盖了首次生成正文。
- 后端随后识别出碎片并改用基于证据包拼装的兜底报告，造成正文长度和结构显著跳变。

因此，问题不来自输入包差异、24 万字符压缩策略或 DeepSeek 摘要，而来自自动修订结果覆盖首次生成结果。

## 3. 设计决策

采用“生成 + 首轮只读质检”的两次模型调用链路。

选择该方案的原因：

1. 删除自动修订可消除本次已经确认的碎片覆盖路径。
2. 保留首轮 Dify 质检，可继续识别主辅材料混淆、无依据事实、未解析附件误用、核心规则或表格遗漏、摘要化和过度推断等语义问题。
3. 当前后端规则门禁主要覆盖部分硬事实、结构、分析深度和技术提示词，不能完整替代模型语义质检。
4. 严重问题路径由最多四次模型调用缩减为固定两次，降低耗时、超时和长 JSON 契约失败概率。
5. 已关闭的不支持事实自动修复或删除行为保持关闭；质检只阻断交付，不自动改正文。

不采用“Dify 只保留生成节点”作为本次方案。该方案虽然固定为一次模型调用，但会立即失去现有语义质检，而当前后端门禁尚不足以补齐企业、产品、规格、需求量和语义性过度推断检查。

## 4. 范围

### 4.1 本次包含

- 修改并发布 `.87` 新 Dify 的首次报告工作流。
- 保留证据包获取、证据包解析、证据包有效性判断、首次生成、首次生成解析和首轮质检。
- 将首轮质检改为只读判断，不再路由到自动修订。
- 新增或收紧首次生成正文的可用性判断，防止提示词片段、JSON 契约片段或明显残缺正文被当成正常报告。
- 保留后端碎片检测、本地质量门禁、`needs_manual_review` 状态和兜底能力。
- 记录最终正文来源及各阶段正文长度，便于区分首次生成与后端兜底。
- 仅在 `.87` 部署后进行服务器验证。

### 4.2 本次不包含

- 不修改 `.88` 旧服务器或 `.86` 旧 Dify。
- 不修改新旧环境的字符或 UTF-8 字节容量策略。
- 不启用 `ENABLE_EVIDENCE_SUMMARY_LLM`。
- 不修改证据摘要提取、二次压缩或表格提取逻辑。
- 不引入新的报告自动扩写、自动删改或自动事实修复。
- 不重构长 Markdown 从 JSON 中传输的整体契约；该项保留为后续独立优化。
- 不在本地运行项目、模型请求、HTTP 测试或 Docker 测试。

## 5. 新工作流

### 5.1 数据流

1. `Fetch Evidence Pack` 按 `pack_id` 获取 `.87` 后端提供的紧凑证据包。
2. `Parse Evidence Pack` 验证 JSON、`pack_id` 和主材料。
3. `Evidence Pack OK?` 失败时返回明确失败结果，不调用模型。
4. `Generate Report JSON` 基于证据包生成唯一初稿。
5. `Parse Generation JSON` 解析初稿并执行基础正文可用性检查。
6. 初稿不可用时，返回生成失败或碎片诊断，由后端进入现有兜底路径并标记 `needs_manual_review`。
7. 初稿可用时，进入 `Quality Check Round 1`。
8. `Parse Quality JSON` 解析质检结果。质检解析失败按阻断问题处理，不修改初稿。
9. `Final Initial Result` 始终输出首次生成的标题和正文：
   - 质检通过：Dify 状态为 `finished`。
   - 质检不通过或质检结果无法解析：Dify 状态为 `needs_manual_review`。
10. 后端继续执行碎片检查和本地质量门禁；后端可以把 `finished` 降级为 `needs_manual_review`，不得因质检失败自动重写报告。

### 5.2 删除的节点和路由

- `Quality Gate` 中通往自动修订的分支。
- `Revise Report JSON`。
- `Parse Revision JSON`。
- `Quality Check Round 2`。
- `Parse Revised Quality JSON`。
- `Final Revised Result`。
- 上述节点之间的全部边。

如果为了安全回滚而暂时保留未连接节点，它们不得处于已发布工作流的可达路径，且最终发布版本必须能够从运行记录证明未调用这些节点。

## 6. 首次生成保护

删除自动修订后，方案 A 中“坏修订回退初稿”的保护不再需要；其保护目标前移到首次生成验收。

`Parse Generation JSON` 或后端生成结果归一化必须至少验证：

- `report_markdown` 是非空字符串。
- 正文不是省略号、错误提示、提示词说明或 JSON 契约说明。
- 正文不以明显中间列表、表格行或第二章以后内容开头。
- 在高证据量材料下，正文不得短到明显无法形成导语和主体结构。
- 正文至少包含导语或第一章节，以及后续主体章节。
- 正文不得包含“报告内容”“双引号转义”“JSON 格式”等已知契约残片。

这些检查只决定“接受初稿”或“标记为不可用”，不对正文进行补写、删句或事实修复。

如果初稿不可用：

- 不调用自动修订模型。
- 后端可以继续使用现有保守兜底报告。
- 状态必须为 `needs_manual_review`。
- 必须记录 `candidate_source=backend_pack_fallback` 和明确失败代码。

如果初稿可用：

- 最终正文必须与首次生成解析后的正文一致。
- 质检节点只能附加问题和状态，不能改变正文。
- 必须记录 `candidate_source=initial_generation`。

## 7. 质检与状态语义

首轮 Dify 质检继续检查：

- 无证据事实、数字、日期、主体和价格。
- 主材料与辅助材料角色混淆。
- 把未解析附件当作已读取全文。
- 遗漏主材料核心规则或重要附件表格字段。
- 只有材料摘要、缺少有依据的影响分析。
- 过度推断、绝对化表述和提示词或 JSON 混入正文。

状态规则：

| 条件 | Dify 状态 | 后端最终状态 |
| --- | --- | --- |
| 初稿可用且首轮质检通过 | `finished` | 本地门禁通过后可交付，否则降级 |
| 初稿可用但首轮质检不通过 | `needs_manual_review` | `needs_manual_review` |
| 初稿可用但质检 JSON 无效 | `needs_manual_review` | `needs_manual_review` |
| 初稿不可用并启用后端兜底 | `needs_manual_review` | `needs_manual_review` |
| 证据包无效或无可用正文且兜底失败 | `failed` | `failed` |

`.87` 现有严格检测、本地质量门禁和不支持事实自动修复开关保持原值。

## 8. 可观测性

运行记录和诊断至少应能区分：

- `candidate_source`: `initial_generation` 或 `backend_pack_fallback`。
- `generation_report_chars`: 首次生成正文长度。
- `final_report_chars`: 最终正文长度。
- `qa_passed`: 首轮质检是否通过。
- `qa_issue_count`: 首轮质检问题数量。
- `generation_validation_code`: 初稿校验结果或失败代码。
- Dify 总耗时和最终状态。

日志不得输出证据包全文、报告全文、API 密钥或认证请求头。

## 9. 部署与回滚

只部署到 `.87`：

1. 导出并保留当前已发布的新 Dify 工作流版本。
2. 保留 `.87` 当前后端代码和运行配置备份。
3. 修改并发布新 Dify 工作流。
4. 如首次生成保护需要后端配合，仅部署对应最小后端改动。
5. `.88` 和旧 Dify 不连接、不修改、不重启。

回滚时先恢复 `.87` 上一个 Dify 已发布版本；如包含后端改动，再恢复对应后端版本。运行历史和报告文件不删除。

## 10. 验证

遵守“不得在本地运行项目”的约束：

- 本地只允许静态查看、编辑、差异检查和文档检查。
- 所有项目运行、HTTP、模型和 Docker 验证仅在 `.87` 完成。

服务器验证使用同一份浙江主材料连续生成两次，记录：

- 两次证据包最终字符数及哈希是否一致。
- 两次 `candidate_source` 是否均为 `initial_generation`。
- 是否还出现 `OUTPUT_TRUNCATED`、`Q_DIFY_FRAGMENTARY_REPORT` 或后端兜底。
- 首次生成和最终正文长度。
- 首轮质检结果、问题数和最终状态。
- Dify 总耗时。

本次验收条件：

1. 已发布工作流的可达路径只有一次生成和一次只读质检模型调用。
2. 质检失败时正文仍与首次生成正文一致。
3. 不再因内部自动修订产生提示词或 JSON 片段覆盖初稿。
4. 两次浙江运行均不因修订链路进入后端兜底。
5. 严格检测和本地质量门禁继续生效。
6. 不支持事实自动修复或删除保持关闭。
7. `.88` 服务、配置、代码和运行状态没有变化。

报告篇幅仍由证据覆盖和首次生成控制。本次不以固定字数差作为唯一验收指标；如果两次均来自首次生成但篇幅或内容覆盖仍明显不稳定，应作为生成提示词或生成契约的下一项独立优化，不重新引入自动修订链路。
