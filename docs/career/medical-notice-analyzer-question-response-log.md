# 1. Evidence Pack 是否需要像 RAG 一样提前离线处理

## 问题

日采集约一万条公告，是否应该全部提前完成附件下载、OCR、表格解析和 Evidence Pack 构建，让用户点击后直接生成报告？用户选择材料后再处理，还算不算预处理？

## 结论

采用：

> **全量轻处理 + 热点预处理 + 用户选择后按需深处理 + 内容哈希缓存复用。**

- 全量轻处理：所有公告做元数据清洗、正文去噪、内容哈希、文件类型识别、去重和业务分类。
- 文档资产预处理：对高价值或高频材料提前下载附件并解析，形成可复用`ParsedDocument`。
- 任务级Evidence Pack组装：用户选择主材料、辅助材料和分析目标后，再组装本次任务证据包。

## 面试表述

> 我没有对每天近万条公告执行同等成本的深度解析，而是将离线文档资产处理与在线任务证据组装拆开。全量数据只做低成本清洗和分类，高价值公告提前解析，其他材料按需处理，并通过`source_hash`和`parser_version`复用缓存。

# 2. 专用解析器与 Apache Tika、MarkItDown 如何选择

## 结论

> **统一解析接口 + 关键格式专用适配器 + Tika/MarkItDown通用兜底。**

```text
PDF   -> pypdf等文本提取 -> 低文本密度时OCR -> 通用解析器兜底
DOCX  -> python-docx -> 通用解析器兜底
DOC   -> LibreOffice受控转换 -> DOCX解析 -> 通用解析器兜底
XLSX/XLSM -> openpyxl(read_only/data_only，不执行宏) -> 通用解析器兜底
XLS   -> xlrd或受控转换 -> 通用解析器兜底
未知格式 -> Tika或MarkItDown
```

| 字段 | 含义 | 为什么需要 |
|---|---|---|
| `parser_name` | 实际解析器 | 比较解析质量和定位故障 |
| `parser_version` | 解析规则版本 | 判断缓存是否失效 |
| `fallback_used` | 是否进入兜底 | 统计主解析器失败率 |
| `parse_status` | 成功、部分成功或失败 | 决定是否生成或转人工 |

安全要求：文件魔数和扩展名双校验、大小/页数/行数上限、压缩包防路径穿越、宏不执行、外链不自动访问、解析进程资源隔离。

# 3. 重要信息未进入证据包时如何发现和兜底

如果信息没有进入完整Evidence Pack，也没有进入模型输入，模型不应该可靠覆盖它。质量评估必须覆盖：

```text
Raw Source -> Parsed Asset -> Full Evidence Pack -> Compact Payload -> Report
```

发现必需主题缺失时，回到完整解析产物定向检索，必要时使用受约束Fact Extractor补建带`source_ref`的新A/B证据；仍找不到则`needs_manual_review=true`。

# 4. 现有证据包构建方法是否合理

当前方案作为受控领域工程原型合理，优点包括主辅材料分离、专用解析、Full Pack与Compact Payload分离、A/B/C分层、Mandatory Evidence保护、解析告警和Claim-Evidence质量门。主要不足是复杂文档解析边界、规则Recall上限和缺少系统Source-to-Evidence标注评测集。

# 5. LangChain、LangGraph 和 HTTP 调用的上下文限制

LangGraph负责State、Node、Edge和执行路由；LangChain提供统一模型调用接口；HTTP负责传输。它们都不会自动替应用控制上下文。

| 字段 | 含义 |
|---|---|
| `model_context_tokens` | 模型总上下文窗口 |
| `estimated_input_tokens` | 本次输入Token估算 |
| `reserved_output_tokens` | 为报告输出预留Token |
| `safety_margin_tokens` | 工具消息和估算误差余量 |
| `application_input_cap_chars` | 应用字符硬上限，例如240000 |

应用最终输入必须同时满足字符硬上限和Token预算。

# 6. 完整数据流第 0～11 步分别存在哪里

- MySQL：公告、客户任务、状态、版本、关系、反馈、偏好候选和指标汇总。
- MinIO：原始附件、解析产物、Full Evidence Pack、Compact Payload、ReportIR、Markdown、DOCX/PDF。

- LangGraph State：小型状态与对象引用。
- Celery消息：只传`run_id`、`pack_id`等标识。

# 8. 用户反馈修订和公司内部资料 RAG 如何设计

## 原结论

反馈分为样式/结构修改、当前公告补证、共享知识扩展。共享知识扩展需要构建`revision_evidence_pack`，不能把历史项目事实覆盖为当前项目事实。

## 更新记录：2026-08-04

- 包装完成态采用公司GraphRAG，组合关键词、向量、知识图谱、结构化过滤和Rerank。
- 纯样式反馈也必须携带原Evidence Pack或受限事实引用，不能只把“报告+反馈”交给模型。
- 用户自助修订最多3轮，由`user_revision_count`计数；超过3轮或仍有阻断问题转人工。
- 网络重试、Celery重复投递和同一轮模型重试不计入用户修订次数。
- 用户反馈日志与偏好记忆分开；只有稳定样式偏好可以形成候选记忆，且必须用户确认后生效。

# 10. 基础证据包与 LLM 压缩是否会造成信息损失

## 原结论

不能承诺100%无损。目标是原始资料可追溯、关键事实强制保真、压缩损失可量化、异常可转人工。

## 更新记录：2026-08-04

- `application_input_cap_chars=240000`只表示应用硬上限，不表示应把模型输入压到接近24万字符。
- 必须为系统提示词、当前任务、偏好上下文、工具消息、输出Token和估算误差预留空间。
- 最终以Token估算校验为准。
- LLM压缩失败时使用规则压缩；仍超限则分阶段生成。
- Mandatory Evidence不能保留时，任务不得强行生成，进入人工复核。

# 11. A 类证据与 B 类证据是否冗余

A类保存“原文是什么、在哪里”；B类保存“程序如何标准化理解原文”。B类必须记录`derived_from`、`extractor_version`、`normalized_value`和`source_hash`。两者是有意冗余，不是两份独立真相。

# 13. 哪些指标评估报告、模型、检索和系统

# 14. Agent State 是什么以及为什么需要它

Agent State是节点间共享的数据快照，不是状态机本身。State、Node、Edge和Checkpoint共同组成有状态工作流。State只保存小型状态和对象引用，大对象进入MinIO。

# 15. Celery 的基础知识和项目中的定位

Celery负责任务何时执行、在哪个Worker执行、队列路由、超时和重试；LangGraph负责单次任务内部节点和条件边。客户化后拆分附件、生成、质检、修订、导出和评测队列，按积压和等待P95扩缩容Worker。

# 16. 通过共享 RAG 将内部工具升级为客户产品是否合理

# 20. 用户总结的完整数据流是否正确以及如何补齐工程机制

## 问题

用户按照主辅材料、证据构建与压缩、Prompt生成、质检、修订、二次质检、后端校验、Word导出、用户反馈和记忆沉淀总结了完整链路。哪些内容正确，哪些与既有包装冲突，怎样补齐每一步的兜底、重试、超时、安全和并发机制？

## 总体判断

整体方向约**75%正确**，主链路顺序基本合理，但有六个必须修正的关键点：

1. 辅助材料不只限于“项目公告类型”，还包括政策、历史轮次、地区规则、公司审核分析和风险规则。
2. GraphRAG返回的是候选资料，不是可直接进入报告的事实；候选资料仍需解析并构建A/B证据。
3. C级证据不是推理结论。推理、风险判断和建议属于独立Analysis Layer。
4. 24万字符是应用硬上限，不应将输入尽量压满；必须预留Prompt、输出Token和安全余量。
5. 后端超时、重试、Watchdog和并发控制贯穿每个节点，不是二次质检之后才执行。
6. 用户反馈不能只用“当前报告+意见”修订；至少要带原Evidence Pack。长期记忆必须经过候选提取和用户确认。

## 第0步：鉴权、限流与任务创建

用户总结中缺少该步骤。客户请求进入FastAPI后执行鉴权、账号额度、令牌桶限流、参数Schema、材料数量、幂等和权限检查；随后在MySQL事务创建`run_id`、材料关系和Outbox事件，再由Celery异步执行。

- 输入：`customer_id`、`requested_by_user_id`、`idempotency_key`、分析目标、材料ID。
- 输出：`run_id`、`status=queued`。
- 存储：MySQL任务表和Outbox；Redis只接收后续队列消息。
- 兜底：Redis不可用时Outbox保留，恢复后补投。
- 重试：客户端重试使用相同幂等键，返回原`run_id`。
- 超时：API只完成接单，不等待模型；目标提交P95小于200ms属于模拟指标。
- 安全：客户只能选择系统已有资料；服务端重新校验ID和范围。
- 并发：单客户和全局双层限流，防止单客户占满队列。

## 第1步：主材料与GraphRAG辅助材料

- 主材料：用户显式选择1～3条项目公告。
- 辅助材料：0～10条，可手动选择，也可由GraphRAG自动召回。
- GraphRAG：关键词、向量、知识图谱关系、地区/品类/阶段/时间/`source_scope`过滤、Rerank、去重和有效期过滤。
- 默认可先召回更大的候选池，再选取1～10条最终材料；不能把初始Top-K直接等同于最终证据。

兜底与工程机制：

- GraphRAG不可用：降级为关键词+结构化过滤；仍不可用时仅使用用户手动选材并显示召回降级告警。
- 超时：查询理解、三路召回和Rerank分别设置超时，总检索超时后返回已完成的高置信候选。
- 重试：只对网络、服务繁忙和短时存储故障重试；空召回不重复轰炸服务。
- 安全：先做权限与`source_scope`过滤，再将内容返回任务；过期规则按`effective_date`过滤。
- 并发：关键词、向量和图关系可以并行召回，但使用独立并发池和超时预算。

## 第2步：正文清洗、附件解析和ParsedDocument缓存

用户说“正文已经是MySQL中的文本文档”不够准确。MySQL通常保存HTML正文和元数据，系统清洗成`content_text`。附件解析完成态采用：PDF文本提取后按低文本密度触发OCR；DOCX用`python-docx`；XLSX/XLSM用`openpyxl`做结构、统计和有限样例；DOC/XLS使用受控转换或通用解析器兜底。

- 输入：MySQL公告记录、附件元数据、MinIO原始附件。
- 输出：`ParsedDocument`，包含文本、表格、页码/行列定位、状态、告警和哈希。
- 存储：大解析产物在MinIO；MySQL保存`parser_name/version`、状态、对象Key和哈希。
- 缓存：`source_hash + parser_version`相同则复用。
- 兜底：主解析器→OCR/受控转换→Tika或MarkItDown→部分成功/人工复核。
- 重试：下载失败、对象存储短时失败可重试；文件损坏、密码保护和不支持格式不盲目重试。
- 超时：下载、OCR、每文件解析和整组附件分别超时。
- 安全：文件魔数、大小、页数、行数、压缩比检查；XLSM不执行宏；ZIP防路径穿越；解析进程限制CPU/内存。
- 并发：不同附件可并行；相同附件用分布式锁避免重复OCR。

## 第3步：Full Evidence Pack、Fact Layer与Analysis Layer

Evidence Pack主要由确定性解析、业务规则、词典、正则和结构化提取器构建。“主要靠正则”表述过窄。复杂表头或语义可用受约束LLM生成候选，但必须校验。

- A级：原文、表格单元格等直接证据，包含`source_ref`。
- B级：A的标准化事实，包含`normalized_value`、`derived_from`、`extractor_version`和`source_hash`。
- C级：摘要、生成指导、告警、诊断和已确认的样式偏好等辅助内容，不能独立支撑事实。
- Analysis Layer：推理、风险和建议，引用`supporting_fact_ids`并记录置信度、风险和不确定性。

正确示例：

```json
{
  "fact_id": "fact_deadline_001",
  "field": "procurement_start_date",
  "raw_value": "5月20日",
  "normalized_value": null,
  "evidence_ids": ["ev_a_001"],
  "uncertainty": "原文未明确年份"
}
```

```json
{
  "analysis_id": "analysis_prepare_001",
  "conclusion": "企业应在项目开始前完成材料准备",
  "supporting_fact_ids": ["fact_deadline_001"],
  "confidence": 0.78,
  "risk_level": "medium",
  "uncertainty": "未掌握企业当前准备进度"
}
```

不能在原文没有年份时擅自标准化出具体年份。

兜底：规则未识别→受约束LLM候选→Schema与来源校验→仍不确定则保留未知并转人工。冲突事实不能自动任选一个。

## 第4步：Compact Payload二次压缩

24万字符作为`application_input_cap_chars`硬上限可以接受，但不能压到接近24万作为实际输入目标。需要同时维护Token预算。

- 先去重、删除模板噪声、保留Mandatory Evidence。
- 再进行规则压缩；仍过长时使用LLM分块压缩。
- 最后估算Token，扣除系统Prompt、任务Prompt、偏好、工具消息、输出Token和安全余量。
- 仍超限则使用`staged_generation`，按章节或材料分阶段生成。

兜底：LLM压缩失败→规则压缩；Mandatory Evidence无法100%保留→不强行生成，转人工。

## 第5步：Prompt组装与报告生成

用户提出的系统Prompt、当前任务Prompt和用户偏好三部分方向正确，但应增加Evidence Context，并明确优先级：

1. 系统规则与输出Schema；
2. 当前任务指令；
3. Compact Payload与来源引用；
4. 用户已确认的结构化偏好Profile。

偏好只能控制长度、表格比例、重点顺序和表达风格，不能修改事实。公告正文、附件、RAG资料和用户反馈都视为不可信数据，用分隔符包裹，防止提示词注入。

生成节点使用DeepSeek V4 Pro，输出ReportIR和Markdown。模型调用设置连接/读取/总超时、并发信号量、Token上限、Schema校验和版本记录。限流或网络失败指数退避；Schema失败可进行一次受控格式修复，不能无限重试。

## 第6步：第一次质量检查

质检不只是检查发布机构、时间和标的物，还包括：

- ReportIR Schema和非空输出；
- 必需章节与关键主题；
- 数值/日期Exact Match；
- 附件状态一致性；
- Claim-Evidence支持和来源定位；
- C级被误当事实；
- 历史项目事实泄漏；
- 禁用表达与高风险无证据结论。

规则质量门和DeepSeek V4 Flash语义质检输出统一`QAResult`，状态为`passed`、`needs_fix`或`blocked`。DeepEval不属于同步阻断门，保持异步旁路。

## 第7步：定向修复

方向正确，但不是把问题段落无限交给模型重写。

1. 先做确定性修复：结构、空字段、无证据表格行、禁用表达。
2. 再把目标段落、问题码、允许使用的A/B证据和禁止新增事实约束交给DeepSeek V4 Flash。
3. 生成新ReportIR版本，并记录`repair_actions`和前后diff。
4. `auto_repair_count`最多2次。

并发安全：报告版本使用乐观锁；两个修复任务不能覆盖同一基线版本。

## 第8步：二次质检、最终持久化与交付判断

二次质检使用与第一次相同的门禁。通过后执行最终后端校验：ReportIR/Markdown一致、对象哈希、版本关系、MySQL/MinIO持久化、状态迁移和`deliverable`。如果仍存在高风险无证据事实、关键附件失败或阻断问题，则不能作为正式可下载报告交付，转人工。

Watchdog、超时和重试贯穿每个节点；最终步骤只做状态收口和一致性校验。

前端立即展示确定性指标，例如A/B支持率、无证据断言数、缺失主题、告警和可交付状态。DeepEval显示`pending`，异步完成后再更新评分；Judge不可用不阻塞报告。

## 第9步：Word导出

只有`deliverable=true`的版本允许正式导出。DOCX由ReportIR受控渲染，文件名清洗、模板和图片白名单、短时签名下载链接。导出失败单独重试，不重新生成报告。

## 第10步：用户反馈与补证修订

预制按钮和自由文本都先进入统一反馈记录。不能因为是预制按钮就只把“意见+最终报告”交给模型，至少需要原Evidence Pack。

- 样式/结构：当前报告+反馈+原Evidence Pack。
- 当前公告补证：回到完整ParsedDocument定向检索并补建证据。
- 跨地区/历史/政策扩展：GraphRAG召回，构建`revision_evidence_pack`后局部修订。

“新疆与山东挂网对比”可先召回1～3条高相关材料，但数量应由证据充分性决定，最多不超过辅助材料上限10条。

用户自助修订最多3轮；超过3轮或仍有阻断问题转人工。`user_revision_count`只在一轮修订成功产生新版本后递增。

## 第11步：偏好记忆候选与沉淀

用户反馈日志、审计记录和长期偏好记忆必须分开。

- 只抽取稳定样式偏好，不抽取公告事实、一次性任务要求和敏感数据。
- 候选状态：`pending`；用户明确同意后变为`approved/active`。
- 保存来源反馈ID、适用范围、版本、创建时间、过期时间和撤销状态。
- 用户可以查看、修改和删除。
- 记忆只影响风格，优先级低于系统规则、证据和当前指令。
- 不进入共享GraphRAG或公司知识事实库，不得跨客户复用。

## 跨步骤工程机制矩阵

| 机制 | 统一规则 |
|---|---|
| 幂等 | `run_id + node_name + input_hash`；任务创建使用`customer_id + idempotency_key`唯一约束 |
| 重试 | 仅网络、限流、短时存储故障重试；指数退避+抖动；不可恢复错误直接失败或人工 |
| 超时 | API、下载、OCR、解析、检索、模型、导出、节点和整任务分层超时 |
| Watchdog | 检查`heartbeat_at`、`current_node`和`watchdog_deadline_at`，恢复卡死任务或转人工 |
| Checkpoint | 每个成功节点保存输入/输出指纹和最后完成节点，重试从安全点继续 |
| 并发 | 队列隔离、模型信号量、附件并行、相同附件分布式锁、报告版本乐观锁 |
| 安全 | 鉴权、租户审计、资料范围过滤、文件沙箱、Prompt注入隔离、日志脱敏、短时下载授权 |
| 可观测性 | OpenTelemetry关联`run_id/trace_id`，记录排队、节点、检索、模型、存储、重试和成本 |
| 降级 | GraphRAG→关键词/手选；OCR/解析器切换；LLM压缩→规则压缩；DeepEval失败不阻塞 |

## 面试表述

> 这条链路不是简单的“RAG召回后让模型生成，再质检两次”。我先在FastAPI层完成鉴权、额度、幂等和可靠入队；主材料决定当前事实范围，GraphRAG只负责从共享公开库和公司审核库召回辅助候选，候选仍要解析成可追溯A/B证据。C级只保存辅助信息，推理结论进入独立Analysis Layer。完整Evidence Pack永久保留，24万字符只是应用硬上限，模型实际输入还要预留Prompt和输出Token；超限时规则压缩、LLM受约束压缩或分阶段生成。报告经过规则门和语义质检，最多自动修复两次；确定性质量结果同步展示，DeepEval异步旁路。用户反馈最多自助修订三轮，需要补证时重新构建revision evidence pack。长期记忆只保存经用户确认的稳定样式偏好，不能污染事实或跨客户共享。每个节点都有幂等、Checkpoint、超时、可恢复重试、并发池和OpenTelemetry Trace。
