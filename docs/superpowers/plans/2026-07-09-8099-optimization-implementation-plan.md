## 3. 不可变硬约束

1. 正式 Markdown、ReportIR、FormalBody 和 Word 正文禁止出现：原文未披露、需人工核验、需人工复核、证据不足、无法确认、请核验、建议人工确认、资料未显示、未在原文中找到、根据有限信息、以上内容需复核、待确认、待核实。
2. 上述表达只能进入 diagnostics、UI、run JSON、测试报告或日志。
3. 事实没有 evidence_pack 支撑时，只能删除、收窄或使用 evidence_pack 已有事实重写，不能创造事实。
4. memory、memory_items、history 和 diagnostics 不能作为事实来源，只能用于结构、风格、历史偏好和问题定位。
5. 必须区分 draft_word_export_available、final_word_export_available、deliverable、needs_manual_review。
6. Word 不可下载时，URL、文件名、文件路径和其他下载定位字段必须为空或隐藏。

8. evidence_pack 第一阶段结果不超过 80000 字符时不得改变；超过时按既有分级策略压缩，最终不得超过 80000。

10. 不提交密钥、.env、临时文件、缓存、备份、运行产物、8100 目录或无关脏改动。
11. 数据库材料身份固定使用 menu_code + articleid，不能只使用 articleid、标题或展示字段。
12. 任一定向测试失败必须立即停止，不能留到后续集成节点处理。
13. 所有 RED/GREEN、定向、回归、全量、容器、固定数据和 Word 测试只允许在 `192.168.34.88` 测试服务器执行；Windows 工作站只用于编辑、Git、制品生成和 SSH 操作，不启动本地服务、容器或真实数据测试。

## 4. 统一验证机制

### 4.0 服务器单环境原则

1. 唯一测试环境为 Ubuntu 测试服务器 `192.168.34.88`；正式测试入口为 `http://192.168.34.88:8099`。
2. 不在 Windows 工作站运行 unittest、pytest、compileall、Docker、固定 3/10、真实数据分析或 Word 扫描。
3. M1 的 RED/GREEN 和模块回归在服务器隔离候选目录或候选容器执行，不部署 8099；候选目录不得读取或覆盖生产挂载数据。
4. M2/M3 从已推送且 SHA 一致的 clean commit 构建制品，完成服务器备份后部署 8099，再执行全量、固定数据、Word 和接口验证。
5. baseline、artifact 和测试报告的环境统一标记为 `server_test`；不得伪造 `local`、`online` 或双环境结果。
6. 服务器部署后测试失败即视为发布失败，必须按回退规则恢复上一安全 SHA、镜像、配置和受影响数据。

### 4.1 M1 微阶段开发验证

M1 用于单一工具、schema、规则或局部实现。

必须执行：

1. 读取本计划、AGENTS.md、当前阶段依赖、范围和非范围。
2. 先写 RED 测试，将仅含当前阶段内容的候选快照上传到服务器隔离目录，并在服务器确认失败原因与目标能力缺失一致。

4. 在服务器执行 compileall；在 Windows 工作站只执行 git diff --check、git status 和禁区检查，这些属于版本范围检查而不是测试。
5. 创建独立 commit，记录依赖、服务器测试命令、结果和所属大阶段。

默认不执行：

- 固定 3/10 真实数据；
- 全量或容器全量测试；
- Word 生成和扫描；
- main 合并、服务器备份、8099 部署；

M1 commit 允许使用 Python dulwich 推送到阶段功能分支，但不得合并 main、不得部署：

## 5. 固定数据、影响指纹与复用规则

### 5.1 Manifest 契约

固定 3/10 manifest 必须记录：

- menu_code、articleid 和稳定材料身份；
- 正文 hash、附件原始内容 hash 或可验证替代 hash；
- 附件数量、格式和角色；
- 预期能力标签；
- 可重放输入和 artifact schema 版本。
- `declared_case_count`、`selected_case_count` 和 `excluded_cases`；每个排除项必须包含稳定材料身份、排除码和观察时间。

身份、正文或附件 hash 漂移时，不得静默覆盖旧基线，必须生成新 manifest 版本并说明原因。

### 5.2 完整固定 10 执行规则

完整固定 10 强制执行两次：

1. S0：在 8099 执行第一次完整固定 10，冻结单服务器环境 baseline B。
2. S2：完成证据、报告结构、质量门禁和 RepairPipeline 后，在 8099 执行第二次完整固定 10 和完整 Word 扫描。

S1 不调用 Dify 生成 10 份完整报告，只在服务器候选环境对 manifest 的全部可用材料执行离线证据链检查：

- 材料身份和正文 hash；
- 附件身份和内容 hash；
- EvidenceItem v2 与 source_ref；
- compact 字符数和分级行为；
- mandatory evidence ID 保留率；
- artifact 可重放性。

S1 离线固定 10 出现以下任一情况时禁止部署：

- 材料身份或附件 hash 无解释漂移；
- compact 最终仍超过 80000 字符；
- 关键证据保留率低于 90%；
- EvidenceItem/source_ref 不完整；
- artifact 不可重放。

S3 以后影响指纹发生变化时，当前发布节点自动从 M2 升级为 M3，并重跑完整固定 10。

### 5.3 关键证据保留率

关键证据保留率定义为：

compact 后仍保留的唯一 mandatory evidence ID 数 / 压缩前唯一 mandatory evidence ID 总数。

计算规则：

- 分子和分母均按唯一 evidence ID 去重。
- 分母大于 0 时结果必须不低于 90%，阶段执行卡可规定更严格的 100%。
- 分母为 0 时记录为 not_applicable，不能伪记为 100%。
- 预期包含 mandatory evidence 的案例若分母为 0，视为证据构建失败。
- 输出 artifact 必须同时保存分子、分母、缺失 ID 列表和计算版本。

### 5.4 影响指纹

影响指纹是以下字段的 canonical JSON 计算 SHA-256，不使用 Dify 输出 hash 或 Word 文件 hash：

- manifest 版本及全部材料、正文和附件 hash；
- EvidenceItem schema/version；
- PDF、表格、OCR 和 VBP 抽取规则版本；
- compact schema、规则和实现版本；
- Dify workflow ID、workflow 版本、prompt 配置 hash、model 配置 hash；
- QualityGate 和 RepairPipeline 规则版本；
- FormalBody、正文清理、Word 渲染和导出版本。

每个 M2/M3 必须记录 Dify workflow ID、workflow 版本、prompt 配置 hash 和 model 配置 hash。远端任一配置发生变化时，原影响指纹立即失效。

若 Dify API 无法提供某项版本或配置内容：

- 保存当时可获得的发布标识和配置摘要；
- 将缺失字段记为 unknown；
- unknown 不允许作为复用依据，当前节点自动升级为 M3。

- 目标：形成适合内部测试服的最终验收和轻量治理方式。
- 范围：汇总质量、性能、历史、备份、运行手册和责任人；定义发布前固定 3 和按需固定 10。
- 非范围：不物理删除 URL 或 Dify；不建设生产级长期治理平台。
- 验证：无代码变化时复用 S4 SHA，不重复部署；影响指纹失效时升级 M3。
- 运行规则：每次功能发布执行固定 3；重大证据/报告变更或影响指纹失效执行固定 10；公司正式演示前可人工触发固定 10。
- 通过标准：S0-S4 证据完整；回退路径可用；8099/8100 隔离；操作手册可执行。
- 回退点：S4 已部署 SHA。
- 预计工期：0.5 至 1 个工作日。

## 8. 条件任务量化触发

## 10. 发布、推送与回退规则

1. 每个阶段使用独立 worktree 和 codex/ 前缀分支，不修改原脏工作区。
2. M1 使用 dulwich 推送功能分支；不得自动合并 main。
3. M2/M3 由 clean commit 构建候选制品，制品 hash、开发工作区 SHA、远端 SHA 和部署 SHA 必须一致；完成备份和部署后只在服务器执行测试。
4. 部署前备份代码、配置、镜像和受影响数据；备份路径和 hash 写入阶段记录。
5. 测试服异常先关闭当前阶段开关；不能恢复时回退上一安全 SHA、镜像和配置。
6. 涉及 schema 或历史数据时，代码回退和数据回退必须分别演练。
7. 不得通过删除历史原始事件、运行记录或用户已有修改完成回退。
8. 每次 M2/M3 完成后暂停，汇报测试、真实数据、Word、SHA、备份、部署、观察和回退结论。

## 12. 阶段执行纪律

1. 每次只执行一个阶段或明确批次。
2. 开始前读取本计划、AGENTS.md；M2/M3 还需读取桌面优化记录。
3. 开始前确认依赖 commit、分支、worktree、验证级别、发布节点和回退点。
4. 发现范围冲突、远端漂移、工作区不干净或影响指纹失效时先停止汇报。
5. M1 完成后汇报 commit、测试、推送状态和所属 M2，不声称已上线。
6. M2/M3 完成后汇报修改文件、测试、固定数据、Word扫描、skip、SHA、备份、部署、观察和是否回退。
7. 未经用户确认不得进入下一阶段。
8. 任何执行卡中的“本地测试”“本地固定数据”“双环境验证”旧措辞均由本节覆盖：不得在 Windows 工作站运行测试，统一改为服务器候选环境或部署后的 8099 验证。
